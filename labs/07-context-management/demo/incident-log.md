# 小店订单 API：故障记录

这份记录来自一个虚构的订单服务练习项目。它故意保留了重复现象、互相矛盾的猜测和未完成验证，练习时请区分事实与推测。

## 2026-04-03：偶发重复订单

客服反馈，少数顾客在付款页连续点击后收到两封确认邮件。数据库中能找到两条订单，金额和商品相同，创建时间相差不到一秒。日志显示两次 POST 请求都返回 201，但请求头里是否带有 Idempotency-Key 尚未核实。有人怀疑是邮件服务重复投递；目前还没有找到相同订单 ID 对应的重复邮件记录。需要先比较两个请求 ID 和订单 ID，不能先把邮件服务当成根因。

## 2026-04-05：请求超时后状态不确定

移动网络较差时，客户端偶尔显示“请求超时”，但用户刷新页面后已经能看到订单。服务端访问日志里，这类请求通常在数据库提交后才断开连接。客户端团队认为服务端处理太慢，服务端团队认为客户端提前取消了请求。当前没有统一的 trace_id，所以两边日志无法逐条对齐。这个现象可能与重复订单有关，也可能只是响应返回太晚，尚未证实。

## 2026-04-08：重试策略讨论

临时补丁把所有连接错误和 5xx 都重试两次。灰度期间请求总量增加约 7%，其中一部分用户报告页面转圈时间更长。指标没有按 endpoint、状态码或客户端版本拆分，因此不能确认增长来自补丁本身。有人建议只重试 502 和 503；另有人提醒，若 POST 没有幂等键，重试可能再创建一笔订单。决定先增加按状态码分组的指标，再讨论重试策略。

## 2026-04-11：429 处理方式不一致

促销活动期间，订单 API 出现 429。Web 客户端会等待响应中的 Retry-After，旧版移动客户端则固定等待 200 毫秒。网关配置确认会返回 Retry-After，但应用日志里没有记录该响应头，无法确认经过代理后它是否仍存在。短等待可能造成请求集中重试，不过目前没有按客户端版本对照的实验。

## 2026-04-13：价格偶尔不一致

一位顾客的确认页显示 39.90 元，后台对账记录为 40.00 元。商品价格在当日凌晨调整过，缓存默认有效期为 15 分钟。客服截图没有商品版本号，订单行也只保存最终金额，没有保存当时使用的单价来源。时钟偏差、旧缓存和促销舍入都被提到过，但现有证据不足以确认原因。后续应为订单保存定价版本并记录折扣计算前后的值。

## 2026-04-15：库存回滚疑问

有两个订单都显示购买了最后一件商品，其中一个后来被取消。代码审查发现库存扣减和订单写入不是同一个事务，但没有复现脚本。开发者认为队列消费者会串行处理，运维配置却显示该队列有四个并发 worker。还需要检查并发配置在生产环境是否与测试环境一致。暂时不要把“单事务”当作已经上线的修复。

## 2026-04-18：测试环境重试差异

同一个超时测试在本地只发出一次请求，在 CI 上偶尔发两次。测试使用真实 sleep 等待 500 毫秒，CI 机器负载波动较大。有人认为是线程竞争，也有人怀疑 HTTP 客户端的默认 retry 配置。测试并没有记录请求计数，也没有固定时间源，因此目前两种解释都没有证据。建议注入时钟并统计 handler 调用次数，再决定是否改客户端配置。

## 2026-04-20：缓存刷新之后仍读到旧值

运营人员修改商品价格后，后台页面立刻显示新价格，结账页有时仍显示旧价格。页面缓存和 API 缓存使用不同的键，刷新按钮只清除后台页面对应的缓存。问题更常出现在多实例环境，但还没有逐实例采样结果。有人提出增加全局缓存失效消息；另一个提议是把价格版本放进缓存键。需要先确认旧值来自哪一层，以及失效事件有没有到达每个实例。

## 2026-04-22：日志中的金额格式

日志查询把 39.9 和 39.90 显示为两个不同的字符串，导致运营误以为存在两种价格。数据库字段是 decimal，日志格式化时却先转成浮点数。这个发现解释了部分对账噪声，但不能解释订单金额确实相差 0.10 元的个案。修复日志格式化之后，还要重新核对 4 月 13 日的订单样本，不能仅凭日志显示变化就认定价格问题解决。

## 2026-04-24：当前结论与待办

已确认：429 的客户端等待策略不一致；库存写入和订单创建不是同一个事务；金额日志格式存在精度展示问题。仍未确认：重复订单与邮件重复是否相关、超时请求是否触发重复提交、促销价格个案的根因。下次排查优先补齐请求 ID、订单 ID、幂等键和定价版本，再做重试或缓存改动。任何结论都应标明来自日志、代码检查还是复现实验。
